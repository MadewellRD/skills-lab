# Skills-Lab v1.1.1

Status: published
Date: 2026-07-25

A disclosure fix. No new skills, no schema change, no change to any desk body.
385 skills across 21 suites, unchanged in count from v1.1.0.

## Why this release exists

`references/presets.md` and `references/tracker-contract.md` ship inside
`006-goliveprompt-skill.zip`. Both carried private operational configuration, so that
configuration was published in a public repository and inside the release assets of
v1.0.0 and v1.1.0.

What was exposed: internal project names and a one-line description of what each system
is, absolute local filesystem paths including two clone locations for the same project, a
repository URL, a machine's drive layout, a dormant clone's last-commit and last-fetch
dates with an approximate stale branch count and an internal gate name, the connector used
to reach that machine, and internal tracker artifact names. `tracker-contract.md`
additionally carried a real project name and a real task title in its schema example.

None of it was needed for the skill to work. All of it is removed.

## What changed

`presets.md` is now generic. It keeps the rule it exists for and the reason behind it: a
root resolver that returns overlapping roots means a search finding one match has not
established that it found the only one, so the root is re-decided every session and some
fraction of the time lands on a dormant clone, where work looks successful and goes
nowhere. Real presets belong in a local file that is never committed.

`tracker-contract.md` keeps the schema and the field rules; its example no longer names a
real project or a real task.

Three skill bodies named a specific local connector where a capability belongs. That is
the same defect the vendor-neutrality gate exists for, so `tools/audit_skills.py` now
gates it alongside the model vendor names.

## Affected earlier releases

The three archives above, as published on v1.0.0 and v1.1.0, contain the exposed content.
They are removed from those releases rather than substituted, because replacing an asset
with a different build would leave those tags advertising checksums that no longer match
the files beside them. Both release bodies point here.

Anyone who downloaded those three archives before this release has a local copy that still
contains the exposed material.

## Tooling changes carried in this release

- `tools/cut_release.py`: a scoped `--suite` cut merges into the repository-wide
  `CHECKSUMS.txt` and `MANIFEST.md` instead of regenerating them from its own subset. It
  previously reduced the root checksum file from 385 lines to 20.
- `tools/validate_release_assets.py`: coverage is discovered from
  `dist/manifests/*-CHECKSUMS.txt` rather than a hardcoded list of seven, so all 21 suites
  are validated. Expected counts come from the JSON manifest rather than from the checksum
  file being tested, and validation runs in both directions so a packaged but unrecorded
  archive is an error.
- `tools/validate_presets.py`: new. Fails when a preset declares a repository root that is
  not an absolute path, unless an explicit allowance records why.
- `.github/workflows/validate-release-assets.yml`: runs on push and pull request, not
  dispatch only. The seven-of-twenty-one coverage gap survived because nothing invoked the
  gate.

## Verify

```bash
python3 tools/audit_skills.py
python3 tools/validate_presets.py
python3 tools/validate_sdlc_suite.py
python3 tools/validate_release_assets.py
```

All four pass on this release. Archives remain deterministic: identical source produces
identical zips, so a checksum mismatch means content genuinely changed.
